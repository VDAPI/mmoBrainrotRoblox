```lua
	created: number, acceptBy: number,
	reason: string?, by: string?, -- cancel reason ("declined" | "timeout" | "left" | "teleport" | "noShow" | "server") and whose
	result: { winner: string?, noRating: boolean? }?,
}
export type Backend = {
	-- SortedMap
	range: (map: string, lo: number?, hi: number?, count: number) -> (boolean, { { key: string, value: any } }?),
	update: (map: string, key: string, fn: (current: any?) -> (any?, number?), ttl: number) -> (boolean, any?),
	remove: (map: string, key: string) -> boolean,
	-- HashMap
	hget: (map: string, key: string) -> (boolean, any?),
	hupdate: (map: string, key: string, fn: (current: any?) -> any?, ttl: number) -> (boolean, any?),
	hremove: (map: string, key: string) -> boolean,
	-- others
	reserve: () -> (string?, string?), -- (accessCode, privateServerId) or nil
	publish: (message: { [string]: any }) -> boolean,
}
```

- Skróty w tekście niżej: `rating` = `entry.ticket.entrant.rating`, `t` = `entry.ticket.joinedAt`, `userId`, `slot`, `name`, `class`, `level` = pola `ticket.entrant`, `bracket`, `mode` = pola biletu. `ArenaQueue` nie definiuje własnego biletu: `Entry` opakowuje bilet S126, a `ArenaQueue.toPairing(record)` składa z rekordu `ArenaRules.Pairing` (dla `take`, D0).
- `ArenaQueue.entryKey(userId, slot)`, `ArenaQueue.queueMap(mode, bracket)` = `"<queuePrefix>_<mode>_<bracket>"` (np. `ArenaQueue_1v1_40_59`; id przedziału napisem z S126), `ArenaQueue.matchKey(id)` = `"ArenaMatch_" .. id`.
- `update` w backendzie: `fn(current)` zwraca `(nowa wartość, nowy sortKey)` albo `nil` (= **nie zapisuj**, jak `UpdateAsync` MemoryStore: zwrot `nil` anuluje). `fn` może być wołane wiele razy (MemoryStore ponawia transformację przy konflikcie), więc każda transformacja jest **czysta** i zależy tylko od `current` i parametrów; wynik decyzji (np. „to ja przestawiłem stan na `accepted`”) czytasz z **zwróconej wartości**, nie ze zmiennej ustawionej w `fn`.

**B2. `Logic/MemoryFake.luau`** (atrapa MemoryStore + Messaging + rezerwacji jako jeden `Backend`). **Nie tworzy drugiego magazynu:** każda SortedMap i HashMap atrapy to `Leaderboard.memoryBoard()` z S124 (z S124; sprawdź w kodzie, `Logic/Leaderboard`), z `score` = `sortKey` (HashMap: `score = 0`). Brakujące w S124 rzeczy dopisujesz **do `memoryBoard`** (nie obok): `range(lo, hi, count, now)` rosnąco z granicami wyłącznymi i ewentualnie wygasanie od ostatniego zapisu; przypadki w `tests/leaderboard.spec.luau` S124 zostają zielone, nowe dopisz tam. `MemoryFake` dokłada tylko to, czego tablica rankingu nie potrzebuje: HashMapy po nazwie, konflikty, błędy, `reserve`, `publish`. `MemoryFake.new(clock: () -> number)` zwraca obiekt z metodami interfejsu `Backend` oraz:

- `update`/`hupdate` z **wstrzykiwanym konfliktem**: `fake:onBeforeCommit(fn(map, key))` wywoływane między obliczeniem transformacji a zapisem; jeśli w nim ktoś zmieni ten klucz, atrapa woła transformację **ponownie** na nowej wartości (jak MemoryStore), najwyżej 5 razy, potem `false`;
- `fake:fail(op, n)`: następne `n` wywołań operacji (`"range"`, `"update"`, `"hget"`, `"reserve"`, `"publish"`, …) zwraca `false` (test błędów i trybu offline);
- `reserve()` zwraca `("fake-code-<n>", "fake-psid-<n>")`; `publish(msg)` dopisuje do `fake.sent` i woła subskrybentów `fake:subscribe(fn)` (wspólna szyna kilku „serwerów” w teście);
- wartości przechowywane jako głębokie kopie (`Util/TableUtil.deepCopy`, jeśli jest czysty; inaczej lokalna kopia), żeby test nie zmieniał stanu „magazynu” przez referencję.

**B3. Wpis kolejki i transformacje** (każda funkcja zwraca transformację dla `update`):
- `ArenaQueue.newEntry(info, now): Entry` (stan `wait`, `t = now`, gdy `info.t` puste; przy ponownym wejściu po nieudanej ofercie serwer podaje stare `t`, żeby gracz nie tracił miejsca).
- `ArenaQueue.refresh(jobId, info, now)`: wpis istnieje i `jobId` się zgadza → ta sama wartość z odświeżonym `rating`, `level`, `name` (przy zmianie przedziału serwer usuwa wpis i dodaje w nowej mapie, D3); wpis `claimed` z `claimUntil < now` → z powrotem `wait` (sprzątanie po martwym organizatorze); brak wpisu albo inny `jobId` → `nil` (nie zapisuj; gracz jest gdzie indziej).
- `ArenaQueue.claim(matchId, now, hold)`: `current == nil` → `nil`; `state == "wait"` albo (`state == "claimed"` i `claimUntil < now`) → `state = "claimed"`, `match = matchId`, `claimUntil = now + hold`; inaczej `nil`. **To jest atomowe przejęcie**: dwa serwery nie mogą przejąć tego samego wpisu, bo `UpdateAsync` na jednym kluczu jest szeregowany, a druga transformacja zobaczy już `claimed`.
- `ArenaQueue.extend(matchId, untilTs)`: przedłuża `claimUntil` tylko, gdy `match == matchId` (gdy oferta istnieje: `claimUntil = acceptBy + acceptGrace`).
- `ArenaQueue.unclaim(matchId)`: `match == matchId` → `wait`, `match = nil`, `claimUntil = nil` (zachowuje `t`); inaczej `nil`.
- Sort key wpisu = `rating` (liczba całkowita). Okno: wprost `ArenaRules.window(waitSeconds)` z S126 (bez kopii w `ArenaQueue`).

**B4. Dobór:**
- `ArenaQueue.pickPartner(me: Entry, candidates: { Entry }, now, opts: { avoid: { [string]: boolean }? }): Entry?`: odrzuca siebie, ten sam `userId`, wpisy `claimed` (nieprzeterminowane), inny przedział/tryb, `avoid` (klucze, które w ciągu ostatnich `declinePenalty` s odrzuciły ofertę z tym graczem, D5); spośród reszty **ten sam warunek co `ArenaRules.pair` (S126)**: `|Δrating| <= max(ArenaRules.window(now − me.t), ArenaRules.window(now − other.t))`, najmniejsze `|Δrating|`, przy remisie starsze `t`, potem klucz. Limit tego samego przeciwnika nie zmienia doboru (jak w S126): mecz po prostu jest bez ratingu (`spec.unrated`).
- `ArenaQueue.shouldInitiate(me, other): boolean` = `me.t < other.t or (me.t == other.t and me.key < other.key)`: parę zakłada serwer gracza, który czeka **dłużej**. Ogranicza to kolizje (dwa serwery rzadko próbują tej samej pary), ale poprawności nie opiera się na tym: tę daje B5.
- `ArenaQueue.lockOrder(a, b): (Entry, Entry)`: kolejność przejmowania po kluczu (mniejszy pierwszy), zawsze ta sama na każdym serwerze.

**B5. `ArenaQueue.tryPair(backend, me, cfg, now, newId: () -> string, jobId): (status, MatchRecord?)`** — cały krok organizatora, synchroniczny względem backendu (status: `"paired" | "local" | "none" | "lost" | "error"`; przy `"local"` drugi zwrot to `ArenaRules.Pairing`):
1. `w = ArenaRules.window(now − me.t)`; `range(queueMap, me.rating - w - 1, me.rating + w + 1, cfg.rangeCount)` (granice wyłączne; inicjuje dłużej czekający, więc jego okno jest większe z dwóch); błąd → `"error"`.
2. `pickPartner`; brak → `"none"`; `not shouldInitiate(me, partner)` → `"none"` (poczeka na tamten serwer).
3. `matchId = newId()`; `first, second = lockOrder(me, partner)`; `update(first, claim(matchId, now, claimHold))`; zwrócone `match ~= matchId` albo błąd → `"lost"`.
4. `update(second, claim(...))`; nieudane → **wycofanie** `update(first, unclaim(matchId))` (błąd wycofania nie szkodzi: `claimUntil` wygaśnie po `claimHold`, a `refresh` właściciela przywróci `wait`) → `"lost"`.
5. `sameJob = me.jobId == partner.jobId`; gdy `sameJob` (obaj gracze tutaj, zawsze na atrapie): **bez** rezerwacji, rekordu i wiadomości: `remove` obu wpisów (błąd nieszkodliwy: przejęcie wygaśnie, a ten serwer nie odnawia kluczy oddanych do `take`) → status `"local"` i `ArenaRules.Pairing` (strony po jednym bilecie, `sides[1]` = starszy, jak w `ArenaRules.pair`), który `take` oddaje do przebiegu S126 (D0, D7). Gdy `not sameJob`: `code, psid = backend.reserve()`; brak → wycofanie obu → `"error"`. (Rezerwacja jest tania: zarezerwowany serwer nie startuje, dopóki nikt na niego nie wejdzie; kontrakt każe rezerwować organizatorowi przed ofertą.)
6. Rekord `MatchRecord` (`state = "offered"`, `acceptBy = now + acceptTime`, gracze posortowani po kluczu, `spec` = `MatchSpec` S126 z migawką ratingów z obu biletów, `origin = "global"`, `venue = "pit"`, `rated = true`, `unrated = {}`: każdy serwer liczy `unrated` swojego gracza z jego `character.arena.vs` przez `ArenaRules.isRated`, serwer areny przed `RunMatch` dla obu) przez `hupdate(matchMap, matchKey(id), fn)` z `fn(current) = if current == nil then record else nil` (nigdy nie nadpisuje istniejącego), TTL `matchTtl`; gdy `psid`: `hupdate(registryMap, psid, …)` z `{ mode = "arena", ref = id }`, TTL `registryTtl` (C1). Błąd → wycofanie obu → `"error"`.
7. `update(first/second, extend(matchId, acceptBy + acceptGrace))` (błąd ignorowany: `refresh` i tak nie zwalnia wpisu z żywym rekordem, B6).
8. `publish({ op = "offer", id, jobs = { j1, j2 } })` (błąd ignorowany: serwery odczytają rekord przy odpytywaniu, D4) → `"paired", record`.

**B6. Oferta i akceptacja (transformacje rekordu):**
- `ArenaQueue.respond(key, accept, now)`: tylko w stanie `offered` i przed `acceptBy`; `accept == true` → `ok = true` gracza; gdy obaj `ok` → `state = "accepted"`; `accept == false` → `state = "cancelled"`, `reason = "declined"`, `by = key`. W innym stanie → `nil`.
- `ArenaQueue.expire(now, reason?)`: `offered` i `now > acceptBy` → `cancelled`, `reason = "timeout"`, `by` = pierwszy gracz bez `ok`; `accepted`/`live` po `now > created + matchTtl - 30` → `void` (sprzątanie). Inaczej `nil`.
- `ArenaQueue.cancel(reason, by)`: z `offered`/`accepted` → `cancelled` (powody `left`, `teleport`, `server`).
- `ArenaQueue.changed(old, new): ("accepted" | "cancelled" | nil)`: czy **ten** zapis zmienił stan (porównanie zwróconej wartości z odczytaną wcześniej; po `hupdate` serwer porównuje `state` przed i po). Tylko serwer, którego zapis przestawił stan na `accepted`, wysyła `publish({ op = "go", id })`; tylko ten, którego zapis dał `cancelled`, wysyła `op = "cancel"`. Pozostali reagują na wiadomość albo na odczyt przy odpytywaniu.
- `ArenaQueue.entryAfter(record, key): "teleport" | "local" | "requeue" | "remove" | "penalty" | "wait"`: co serwer właściciela robi z wpisem gracza po odczycie rekordu (`accepted` → `teleport`; pary `sameJob` nie mają rekordu, B5; `cancelled` i `by == key` z `declined`/`timeout`/`left` → `penalty`; `cancelled` z innym `by` albo powodem `teleport`/`server`/`noShow` cudzym → `requeue` z zachowanym `t`; `done`/`void` → `remove`; `offered` → `wait`; brak rekordu przy `claimed` po `claimUntil` → `requeue`).

**B7. Serwer areny:**
- `ArenaQueue.arrival(record, present: { [string]: boolean }, bootTs, now, cfg): "wait" | "start" | "noShow"`: obaj obecni i załadowani → `start`; minęło `arriveTimeout` od `bootTs` → `noShow` (z listą nieobecnych w drugim zwrocie); inaczej `wait`.
- `ArenaQueue.allowed(record, userId, slot): boolean`: gracz jest w rekordzie z tym slotem i rekord ma stan `accepted` albo `live`.
- `ArenaQueue.returnPlan(attempt: number, returnJob: string?, cfg): { kind: "instance", job: string } | { kind: "public" } | { kind: "kick" }`: próba 1..`teleportRetries` z `returnJob` → `instance`; potem `teleportRetries` prób `public`; potem `kick` (ostatnia deska: gracz wraca, logując się zwyczajnie; komunikat kicka po polsku i angielsku, wzór `DataService.kick`).
- `ArenaQueue.decideMode(info: { privateServerId: string, ownerId: number, registry: any?, joinData: any? }): (mode: "world" | "arena" | "tournament", ref: string?)`: `privateServerId == ""` → `world`; `ownerId ~= 0` (prywatny serwer gracza, nie rezerwacja) → `world`; wpis rejestru z poprawnym `mode` (`arena`/`tournament`) i `ref` (string) → ten tryb; brak rejestru, ale `joinData.TeleportData.serverMode` poprawny → ten tryb (ref z `arenaMatch`/`tourney`); inaczej `world` (zarezerwowany serwer bez wiedzy, po co jest, działa jak zwykły świat: nic nie psuje).
- `ArenaQueue.parseMessage(data): Message?`: odrzuca wszystko poza `{ op = "offer" | "go" | "cancel", id = string (≤ 64 znaki), jobs = { string }? }`.
- `ArenaQueue.scope(s: { backendOk: boolean, studio: boolean, offlineUntil: number, now: number }): "global" | "local"` i `ArenaQueue.localOffer(waited, globalWait, localCandidate: boolean): boolean` (fallback F1).

**D8. Wyścigi — co musi być prawdą (komentarz nagłówka `Matchmaker.luau` i testy H3):**
- Ten sam wpis nie trafia do dwóch meczów: przejęcie `claim` jest jedną transformacją `UpdateAsync` na kluczu wpisu; druga widzi `claimed`.
- Dwa serwery łączące A–B i B–C: wygrywa ten, kto pierwszy przejmie B; drugi wycofuje swoje pierwsze przejęcie (`unclaim`) i próbuje przy następnym odpytaniu.
- Dwa serwery łączące A–B jednocześnie (oba uważają, że ich gracz czeka dłużej — np. równe `t`): `lockOrder` daje tę samą kolejkę przejęć, więc jeden przejmie oba, drugi odpadnie na pierwszym kroku; nigdy nie powstaną dwa rekordy dla tej pary.
- Organizator padł po przejęciu: `claimUntil` wygasa po `claimHold` s, `refresh` właściciela przywraca `wait`.
- Organizator padł po zapisie rekordu, przed wiadomością: serwery graczy odczytują rekord przy odpytywaniu (D4 krok 1).
- Oba serwery jednocześnie wykrywają koniec czasu: `expire` jest transformacją, tylko pierwsza zmienia stan; `changed` mówi, kto wysyła `cancel`.
- Wiadomość `go` zginęła: odpytywanie odczyta `accepted` i teleportuje (najpóźniej po 5 s).
- Gracz wyszedł z gry w trakcie oferty: `Leave` → `respond(false)` z powodem `left` i karą; gdy serwer padł, `expire` po `acceptBy` zrobi to drugi serwer.
- Ten sam gracz nie może być w dwóch kolejkach naraz: ProfileStore blokuje sesję (jedno konto = jeden serwer), a jedna aktywna postać na sesję; wpis ma klucz `userId_slot`, a `pickPartner` odrzuca ten sam `userId`.
- Zegar: `os.time()` (UTC, sekundy) na wszystkich serwerach; czasy w rekordach mają zapas `acceptGrace`, żaden warunek nie zależy od ułamka sekundy.

### F. Fallback i Studio

**F1.** Kontrakt: brak MemoryStore/Teleport albo nikt w kolejce globalnej przez `globalWait = 45` s → propozycja walki lokalnej (jeśli na serwerze ktoś czeka) albo dalsze czekanie. Realizacja:

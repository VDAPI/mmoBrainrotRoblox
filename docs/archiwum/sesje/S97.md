## Kontekst

Właściciel chce wierzchowca od 20. poziomu, którego „można ulepszać”, który ma „różne skiny”, a lepszy można zdobyć „z bossów” albo w przyszłości kupić „za robuxy” (cytat na końcu). Ta sesja dokłada rozwój i zdobycze. Liczby z DESIGN-15 §2, które są kontraktem: poziomy wierzchowca 1–10, mnożnik liniowo `baseMul` 1,6 → `maxMul` 2,0 (czyli +0,0444 na poziom), od 5. poziomu wsiadanie 1,0 s zamiast 1,5 s (`mountTimeFast` od `fastFromLevel`), poziomy startowe bossowych 3 / 4 / 5 / 6, premium jak bossowy, ten sam sufit dla wszystkich, skiny na każdego posiadanego.

**A3. Krzywa ulepszeń `UPGRADE`** (nowa tabela; kształt):

```lua
-- Upgrade to mount level n (DESIGN-15 §2, S97): character level needed, gold and monster parts. The same for every
-- mount (a boss mount starts higher, so it skips the first steps). Gold priced against the level income of the S84
-- model at `level` (tests/Balance.luau); see docs/BALANS.md "Wierzchowce".
export type UpgradeStep = { level: number, gold: number, materials: { { id: string, n: number } } }
local UPGRADE: { [number]: UpgradeStep } = {
	[2] = { level = 20, gold = …, materials = { … } },
	…
	[10] = { level = 90, gold = …, materials = { … } },
}
```

- **Poziom postaci** (`level`) wymagany do ulepszenia na dany poziom wierzchowca (DESIGN-15 milczy; decyzja tej sesji, linia w DECYZJE): 2 → 20, 3 → 25, 4 → 30, 5 → 40, 6 → 50, 7 → 60, 8 → 70, 9 → 80, 10 → 90. Dzięki temu poziom wierzchowca rośnie z regionami, a pełne 10 jest celem końca gry. Wierzchowiec bossowy z wyższym `startLevel` zaczyna wyżej i nie wymaga poziomu postaci, żeby na nim jeździć (tylko `Config.Mount.minLevel`).
- **Materiały** to części potworów z pasma poziomu (sprawdź w `LootTables.PARTS`, że dropią na tych poziomach; jeśli którejś części nie ma w żadnym rodzaju pasma, weź sąsiednią z tego samego regionu), kierunek: 2: `wolf_pelt` 15 + `thick_hide` 10; 3: `werewolf_claw` 12; 4: `werewolf_claw` 20 + `ectoplasm` 10; 5: `ectoplasm` 20; 6: `salamander_scale` 15; 7: `salamander_scale` 15 + `magma_shard` 15; 8: `magma_shard` 20 + `yeti_fur` 10; 9: `yeti_fur` 25; 10: `yeti_fur` 20 + `frost_scale` 15. Przy szansie części ok. 0,3 × 1,5 sztuki to 30–80 zabić rodzajów, które je dają: kilkanaście minut gry na stopień. Bez esencji, Rdzeni i zwojów (nie konkurują z ulepszaniem broni).
- **Złoto** wyceniasz w modelu (G1), nie na oko: `gold(n) ≈ k(n) × dochód poziomu(level(n))`, zaokrąglone do 500, z `k` = 0,4 dla 2–4, 0,55 dla 5–7, 0,7 dla 8–10; cały 1→10 to ok. 5–6 „poziomów dochodu” rozłożonych na 20.–90. poziom. Pasmo do asercji: każdy stopień 0,3–1,0 dochodu poziomu przy `level(n)`, suma udziałów 2..10 w 4–8. Złoto rośnie ściśle z `n`. Dla orientacji (kierunek, decyduje model): 2: ok. 3 000, 5: ok. 18 000, 8: ok. 65 000, 10: ok. 120 000.
- Każda liczba `UPGRADE` dostaje powód w `tools/balance_reasons.luau` (`session = "S97"`; prefiks `Mounts:UPGRADE*` wolno, bo tabela jest nowa, ale w `why` wpisz udział w dochodzie każdego stopnia albo odsyłacz do tabeli w `docs/BALANS.md`). Klucze zrzutu sprawdź w `Balance.dataDump` (format S83: `Mounts:UPGRADE[2].gold`).

### C. Czysta logika (`src/shared/Logic/Mounts.luau`, `src/shared/Logic/Premium.luau`)

Dopisz do modułu S96 (bez API Roblox). Nazwy poniżej są nowe; jeśli S96 ma funkcję o tym samym celu, użyj jej.

**C1. Ulepszanie:**

- `Mounts.canUpgrade(character, mountId: string, inv: { [string]: number }): (boolean, string?, UpgradeStep?)`: `inv` to liczba sztuk materiałów, które gracz ma (serwer liczy przez `InventoryService.Count`, test podaje tabelę). Posiadany = brak losowania (test sprawdza, że `rng` jest nietknięty). Bez parametru szczęścia (zasada: osobno od pity i Fortuny). Nieznany boss → `{}` bez losowania.

- `Mounts.expectedKills(chance): number` = `1 / chance` (wiki, `/mountsim`, raport).

**C3. Widoczność:**

**C4. Wygląd ze skinem:**

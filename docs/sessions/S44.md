## A. GitHub Actions: build i wdrożenie (`.github/workflows/wiki.yml`)

1. `name: Wiki`. Wyzwalacze: `push` na `main`, `pull_request`, `workflow_dispatch` i `schedule` raz w tygodniu (`cron: "17 4 * * 1"`, odświeża „Potwór tygodnia” i „Legendarny przedmiot tygodnia”). Filtr `paths` dla push i PR: `wiki/**`, `src/shared/**`, `tools/wikidump.luau`, `tools/WikiDump/**`, `tools/wikimap.luau`, `tools/WikiMap/**`, `art/icons/**`, `tests/wikidump.spec.luau`, `tests/wikimap.spec.luau`, `rokit.toml`, `.github/workflows/wiki.yml`. Zmiany w serwerze i kliencie gry nie budują wiki.
2. `permissions: { contents: read, deployments: write }`. `concurrency`: grupa `wiki-${{ github.ref }}`, `cancel-in-progress: ${{ github.event_name == 'pull_request' }}` (wdrożenie produkcji nigdy nie jest przerywane w połowie). Ustaw `timeout-minutes: 30`.
3. Jeden job na `ubuntu-latest`, kroki w tej kolejności:
   - `actions/checkout@v4` z `fetch-depth: 0`. Pełna historia jest potrzebna, bo w płytkim klonie `git log -- src/shared` zwraca zły `dataCommit`.
   - `CompeyDev/setup-rokit@v0.1.2` (ta sama akcja i wersja Lune co w `ci.yml`), potem `lune --version`.
   - `actions/setup-node@v4` z `node-version-file: wiki/.nvmrc`, `cache: npm`, `cache-dependency-path: wiki/package-lock.json`, potem `npm ci` w `wiki/`.
   - `npm run data`: eksport, mapy i ikony, tak samo jak lokalnie. Sprawdź, że `scripts/data.mjs` działa na Linux: ścieżki przez `path`, bez `.exe` i bez `powershell`.
   - `node scripts/stale-data.mjs` (A.5).
   - `lune run tests/run.luau` w korzeniu repo. Wdrożenie nie czeka na `ci.yml`, więc testy eksportera muszą przejść tutaj.
   - `npm run check` z env `SITE_URL: ${{ vars.SITE_URL || 'https://vaelthorn-wiki.pages.dev' }}` oraz `PUBLIC_NOINDEX`: `1`, gdy zdarzenie to PR albo gałąź inna niż `main`; w przeciwnym razie `0`.
   - `npx playwright install --with-deps chromium`, potem `npm run qa` (sekcja E). Gdy się nie uda: `actions/upload-artifact@v4` z `wiki/playwright-report` (`if: failure()`).
   - Wdrożenie przez `cloudflare/wrangler-action@v3`: `apiToken: ${{ secrets.CLOUDFLARE_API_TOKEN }}`, `accountId: ${{ secrets.CLOUDFLARE_ACCOUNT_ID }}`, `gitHubToken: ${{ secrets.GITHUB_TOKEN }}`, `command: pages deploy wiki/dist --project-name=${{ vars.CF_PAGES_PROJECT || 'vaelthorn-wiki' }} --branch=${{ github.head_ref || github.ref_name }} --commit-hash=${{ github.sha }}`. Gałąź `main` to produkcja, każda inna to podgląd. Wersję wranglera przypnij jawnie: aktualną sprawdź przez `npm view wrangler version`, a nazwy wejść i wyjść w README akcji.
   - Adres wdrożenia (wyjście akcji, np. `deployment-url`) wpisz do `$GITHUB_STEP_SUMMARY`.
4. **Bez sekretów workflow ma być zielony.** Na poziomie joba ustaw `env: HAS_CF: ${{ secrets.CLOUDFLARE_API_TOKEN != '' && secrets.CLOUDFLARE_ACCOUNT_ID != '' }}`. Krok wdrożenia dostaje warunek `if: env.HAS_CF == 'true' && (github.event_name != 'pull_request' || github.event.pull_request.head.repo.full_name == github.repository)` (PR z forka nie ma sekretów). W przeciwnym razie osobny krok wypisuje `::notice::Brak sekretów Cloudflare — pomijam wdrożenie (docs/WIKI.md → Wdrożenie)`.
5. `wiki/scripts/stale-data.mjs` (czyste funkcje w `scripts/lib/stale-core.mjs`; działa też lokalnie po `npm run data`):
   - Sprawdza `git status --porcelain` dla generowanych plików tekstowych: `wiki/src/data/**`, `wiki/src/styles/tokens.data.css`, `docs/PRZEDMIOTY.md`, `wiki/public/img/maps/**` (S37), `wiki/src/generated/**` (S40).
   - `meta.json` porównuje **bez** `dataCommit` i `dataDate`: eksport zrobiony przed commitem ma poprzedni commit i to nie jest nieaktualność.
   - Obrazów binarnych nie porównuje, bo kodery mogą się różnić między systemami.
   - Przy różnicy w GitHub Actions wypisuje `::warning title=Nieaktualne dane wiki::<pliki>` i listę w `$GITHUB_STEP_SUMMARY` z poleceniem „`npm run data` w `wiki/` i commit”. Lokalnie zwykły wydruk. Zawsze kończy kodem 0, bo strona i tak buduje się ze świeżego eksportu (zapisz tę decyzję).
   - Jeśli ostrzeżenie pojawia się tuż po świeżym `npm run data` na Windows, to błąd determinizmu eksportera (kolejność plików, formatowanie liczb, końce linii). Napraw go w `tools/WikiDump`, nie wyciszaj.
6. Skrypt npm `ci:local` = `npm run data && node scripts/stale-data.mjs && npm run check && npm run qa` (na końcu przypomnienie o `lune run tests/run.luau`). Typowy błąd CI: `npm ci` na Linux nie znajduje `@rollup/rollup-linux-x64-gnu` albo `@img/sharp-linux-x64`, bo lockfile z Windows nie ma opcjonalnych paczek innych platform. Wtedy odtwórz `package-lock.json` aktualnym npm i sprawdź, że zawiera wpisy dla linux.

## B. Instrukcja dla właściciela (`docs/WIKI.md` → nowa sekcja „Wdrożenie”)

Napisz krok po kroku po polsku, z nazwami przycisków. Tę samą skróconą wersję daj w „Instrukcja testu S44”:
1. Załóż darmowe konto Cloudflare (`https://dash.cloudflare.com/sign-up`). Skopiuj **Account ID** (panel Workers & Pages albo prawa kolumna przeglądu konta).
2. Utwórz projekt Pages metodą **Direct Upload**. Nie wybieraj „Connect to Git”: buduje GitHub Actions, bo potrzebny jest Lune. Ścieżka: Workers & Pages → Create → Pages → Upload assets → nazwa `vaelthorn-wiki` → wgraj folder `wiki/dist` z lokalnego `npm run build`. Można też w terminalu: `npx wrangler login`, potem `npx wrangler pages project create vaelthorn-wiki --production-branch=main`. Inna nazwa projektu wymaga zmiennej repozytorium `CF_PAGES_PROJECT`.
3. Utwórz token API: My Profile → API Tokens → Create Token → Custom token. Uprawnienie **Account → Cloudflare Pages → Edit**, Account Resources tylko Twoje konto. Skopiuj token od razu, bo pokazuje się raz.
4. W GitHub: repozytorium → Settings → Secrets and variables → Actions → New repository secret. Dodaj `CLOUDFLARE_API_TOKEN` i `CLOUDFLARE_ACCOUNT_ID`.
5. Actions → „Wiki” → Run workflow (gałąź `main`). Po ok. 10 min adres pojawi się w podsumowaniu runu. Sprawdź `https://vaelthorn-wiki.pages.dev/pl/` i `/en/`.
6. Własna domena: projekt Pages → Custom domains → Set up a custom domain, np. `wiki.<domena>`. Jeśli domena jest w Cloudflare, rekord doda się sam; jeśli nie, dodaj u rejestratora CNAME `wiki` → `vaelthorn-wiki.pages.dev`. Poczekaj na status „Active” (SSL). Potem w Settings → Secrets and variables → Actions → **Variables** dodaj `SITE_URL` = `https://wiki.<domena>` i uruchom workflow ponownie (canonical, sitemap i obrazy OG przejdą na nowy adres).
7. Wpisz `PLAY_URL` (link do gry) i opcjonalnie `DISCORD_URL` w `wiki/src/config.ts` i zrób commit.
8. Na co dzień: każdy PR dostaje adres podglądu (noindex) w podsumowaniu runu. Wycofanie: Pages → Deployments → wybrane wdrożenie → Rollback. Ręcznie w awarii: `cd wiki`, `npm run build`, `npx wrangler pages deploy dist --project-name vaelthorn-wiki --branch main`.
9. Problemy: „Authentication error [code: 10000]” oznacza zły token albo brak uprawnienia; „Project not found” to inna nazwa projektu. GitHub wyłącza harmonogram po 60 dniach bez commitów (włączysz go w Actions → Wiki → Enable workflow). Darmowy plan Cloudflare pozwala na 20 000 plików w jednym wdrożeniu (pilnuje tego `budgets.mjs`). Opcjonalnie: Google Search Console → dodaj domenę → prześlij `sitemap-index.xml`.

## C. Audyt po buildzie (część `npm run check`)

1. `wiki/scripts/budgets.mjs` (rdzeń w `scripts/lib/budgets-core.mjs`) dla każdego `dist/**/*.html`:
   - JS strony to `<script src>`, `<link rel="modulepreload">`, atrybuty `component-url`, `renderer-url` i `before-hydration-url` z `<astro-island>`, ich statyczne importy rekurencyjnie (`import"./x.js"`, `from"./x.js"`) oraz skrypty inline. Suma po gzip, każdy plik liczony raz.
   - Limity trzymaj w jednej tabeli `scripts/budgets.config.mjs`: domyślnie 50 KB, wyjątki z Kontekstu dopasowane wzorcem ścieżki PL i EN.
   - Pagefind (`/pagefind/*`, ładowany dopiero po wpisaniu frazy) tylko raportuj, osobno.
   - Przekroczenie kończy skrypt błędem z listą plików.
   - Ostrzeżenia: CSS strony > 60 KB gzip, HTML strony > 150 KB gzip, pojedynczy obraz > 300 KB, `public/img/mobs` > 10 MB, `public/img/items` > 8 MB.
   - Błędy: liczba plików w `dist` > 19 000 (ostrzeżenie już od 15 000) albo plik > 25 MiB.
   - Raport: tabela 20 najcięższych stron w konsoli i `wiki/.reports/budgets.json` (dopisz `.reports/` do `wiki/.gitignore`).
2. `wiki/scripts/audit.mjs` (rdzeń w `scripts/lib/audit-core.mjs`) dla każdej strony w `dist`:
   - `<html lang>` zgodny z prefiksem adresu, dokładnie jeden `<h1>`, `<title>` niepusty i unikalny w obrębie języka.
   - `meta description`: brak daje ostrzeżenie.
   - Canonical absolutny od `SITE_URL`. `hreflang` pl/en/x-default wskazują istniejące pliki i odwołują się wzajemnie.
   - Strony `noindex` nie są w sitemap. Każdy adres z sitemap istnieje i nie ma `noindex`.
   - `og:image` jest absolutny i plik istnieje w `dist`.
   - Każdy `<img>` ma `alt` (pusty tylko dla dekoracji), `width` i `height`. Żadnych `href="#"` ani pustych linków.
   - **Wycieki (błąd):** kody z `src/shared/Data/Codes.luau` (wyrażenie `code = "…"`) wyszukiwane jako całe słowa z rozróżnieniem wielkości liter (kod równy nazwie gry pomiń z ostrzeżeniem) oraz id z `Config.AdminUserIds` jako całe liczby.
   - **Braki obrazków (ostrzeżenie, lista trafia do „Niedokończone”):** potwór z `monsters.json` bez `public/img/mobs/<id>.webp`, przedmiot bez ikony, gdy atlasy S35 są w repo.
3. `check` = dotychczasowy łańcuch, a po `check-links` dodatkowo `node scripts/budgets.mjs && node scripts/audit.mjs`.

## D. SEO, meta, 404, nagłówki

1. `astro.config` bierze `process.env.SITE_URL ?? SITE_URL` z `src/config.ts`. Canonical, sitemap, `og:image` i robots korzystają z tego jednego źródła.
2. Endpoint `src/pages/robots.txt.ts`:
   - Produkcja: `User-agent: *`, `Allow: /`, `Disallow: /pl/styleguide/`, `Disallow: /en/styleguide/`, `Sitemap: <SITE_URL>/sitemap-index.xml`.
   - Przy `PUBLIC_NOINDEX=1`: `Disallow: /`, a `Base` dodaje `<meta name="robots" content="noindex">` na każdej stronie.
   - Usuń ewentualny `public/robots.txt`.
   - Sprawdź `dist/sitemap-*.xml`: tylko strony indeksowalne, oba języki, adresy absolutne, bez `?`. Jeśli zostanie czas: `xhtml:link` hreflang w sitemap (opcja `serialize` integracji, pary z `alternate()` w `src/i18n/routes.ts`).
3. Domyślny obraz OG dla stron bez własnego:
   - Jeśli jest `scripts/og-images.mjs` (S39), dopisz do jego manifestu wpis `default`: kicker „VAELTHORN WIKI”, tytuł „Oficjalna wiki” / „Official wiki”, podpis z liczbami z `meta.counts`. Wynik trafia do `dist/img/og/<lang>/default.jpg`. Bez S39 użyj `public/img/og/default-art.png` z S38.
   - Do tego `og:image:alt`, `og:locale` z `og:locale:alternate` i `twitter:card=summary_large_image`.
   - Jeśli zostanie czas: osobne warianty dla stron działów (przedmioty, bestiariusz, mapa, klasy, ulepszanie).
4. `public/_headers` (Cloudflare Pages):
   - `/_astro/*`: `Cache-Control: public, max-age=31536000, immutable`.
   - `/img/*`: `public, max-age=86400`.
   - `/pagefind/*`: `public, max-age=3600`.
   - `/*`: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Permissions-Policy: camera=(), microphone=(), geolocation=()`.
   - CSP tylko jeśli zostanie czas, jako `Content-Security-Policy-Report-Only`.
5. 404: sprawdź `dist/404.html`, `dist/pl/404.html` i `dist/en/404.html` (`noindex`, właściwy `lang`, pole szukania, link do głównej). Cloudflare Pages szuka najbliższego `404.html` w górę drzewa katalogów, więc `/en/cokolwiek/` pokaże stronę angielską. Przekierowanie `/` według języka (S36) musi działać też bez JS (`noscript`).

## F. Lighthouse i obrazy

1. Dodaj devDependency `@lhci/cli` i plik `wiki/lighthouserc.cjs`:

   Skrypt npm `lighthouse` = `npm run build && lhci autorun`. Uruchamiaj lokalnie, bez `PUBLIC_NOINDEX` (inaczej spadnie SEO). W CI tylko jeśli zostanie czas: osobny job z `continue-on-error` i raportem jako artefakt, bo wyniki na runnerach skaczą.
2. Poprawiaj w tej kolejności:
   - obraz LCP (render potwora albo bossa, słup światła, mapa): `fetchpriority="high"`, bez `loading="lazy"`, z `width` i `height`;
   - pozostałe obrazy: `loading="lazy" decoding="async"`;
   - `srcset` i `sizes` z gotowych rozmiarów (renderów `-128.webp` i 512, ikon `-64` i `-128`), żeby karty bestiariusza na mobile nie ładowały 512 px;
   - preload 1–2 krytycznych `woff2` (Alegreya Sans 400 latin-ext, Grenze Gotisch 700) i tylko podzbiory latin + latin-ext;
   - wyspy z `client:visible` albo `client:idle` zamiast `client:load` tam, gdzie pierwszy widok i tak jest w HTML;
   - duży DOM (baza przedmiotów, mapa): paginacja albo `content-visibility: auto` poza ekranem;
   - zero błędów w konsoli;
   - zarezerwowana wysokość hero i nagłówków (CLS przy podmianie fontów).
3. AVIF tylko jeśli zostanie czas: `scripts/avif.mjs` (sharp) dla renderów 512 i `<picture>` w `MonsterImage`, ale tylko gdy plik jest co najmniej o 20% mniejszy niż WebP. W przeciwnym razie zostaje WebP (zapisz w „Decyzje”).
4. Tabela wyników do `docs/WIKI.md` → „Stan”: strona × 4 kategorie × JS po gzip. Jeśli strona po poprawkach nie dochodzi do 95 (najpewniej mapa: duży SVG i panzoom), wpisz wynik, przyczynę i to, co próbowałeś. Wyjątek najwyżej przez `assertMatrix` dla tej jednej strony, z komentarzem.
